## 2. 주간 점검 (15분, 매주 월요일)

```bash
scripts/ops/health-report.sh > /tmp/weekly-$(date +%F).txt
```

체크리스트:

- [ ] **알럿 이력** — 지난주 발화한 알럿 목록. 반복되는 것이 있는가?
- [ ] **에러율** — 5xx 비율 추이. 상승 중인가?
- [ ] **p95 응답시간** — `10_NFR.md` §1 목표 대비
- [ ] **트랜스코드 성공률** — 97% 이상인가? 실패 원인 분포는?
- [ ] **DLQ** — 비어 있는가? 있으면 원인 분석 후 처리
- [ ] **디스크** — 각 노드 사용률. 60% 넘었으면 조치 계획
- [ ] **Object Storage** — 총 용량 증가율. 예상 대비
- [ ] **CDN 전송량** — 전주 대비 3배 이상 증가했는가? (어뷰징 신호)
- [ ] **백업** — 7일 연속 성공했는가? 최신 백업 크기가 정상인가?
- [ ] **DB 크기** — 증가율. 특정 테이블이 튀는가?
- [ ] **카운터 드리프트** — 보정 잡이 고친 건수. 증가 추세면 버그 신호
- [ ] **`_ISSUES.md`** — OPEN 항목이 방치되고 있는가?
- [ ] **심사큐** — 미처리 신고가 쌓여 있는가?

**하나라도 이상하면 그 자리에서 이슈로 기록한다.** "다음 주에 보자" 는 금지.

## 3. 월간 점검 (1시간, 매월 1일)

- [ ] **보안 패치** — `unattended-upgrades` 로그 확인. 재부팅 필요한가?
- [ ] **의존성 취약점** — `pnpm audit`. High 이상은 즉시 조치
- [ ] **마이너 버전 갱신** — `pnpm update` (patch/minor만) → `pnpm gate` → 배포
- [ ] **인증서** — 만료일 확인 (Caddy 자동이지만 갱신 로그 확인)
- [ ] **로그 용량** — 로테이션이 실제로 동작하는가
- [ ] **미사용 리소스** — 고아 파일, 오래된 Docker 이미지, 사용 안 하는 볼륨
- [ ] **비용** — VPS + Object Storage + CDN 청구액. 예상 대비 (`10_NFR.md` §7)
- [ ] **성능 예산** — Lighthouse CI 추이. 서서히 나빠지고 있는가?
- [ ] **DB 인덱스 사용률** — `pg_stat_user_indexes` 에서 사용 안 되는 인덱스 발견
- [ ] **느린 쿼리** — `pg_stat_statements` 상위 10개 검토
- [ ] **테이블 팽창** — `VACUUM` 상태, dead tuple 비율
- [ ] **커버리지 추이** — 하락했으면 원인 확인

```sql
-- 사용되지 않는 인덱스 (삭제 후보)
SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes WHERE idx_scan < 50 ORDER BY idx_scan;

-- 느린 쿼리 상위 10
SELECT calls, mean_exec_time, query
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;

-- dead tuple 비율
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0*n_dead_tup/nullif(n_live_tup+n_dead_tup,0), 1) AS dead_pct
FROM pg_stat_user_tables ORDER BY dead_pct DESC NULLS LAST LIMIT 10;
```

**인덱스를 삭제하기 전에** `04_DOMAIN_MODEL.md` §6 의 근거 표를 확인한다.
아직 구현되지 않은 기능을 위한 인덱스일 수 있다.

## 4. 분기 복구 훈련 (2시간)

**백업은 복구를 성공시킨 적이 있을 때만 백업이다.**

```
1. 별도 VPS 또는 로컬에 스테이징 환경 준비
2. 최신 백업을 그곳에 복구 (scripts/ops/restore-db.sh)
3. 앱을 그 DB 로 기동
4. 검증:
   - 로그인 가능
   - 피드에 에피소드 표시
   - 영상 재생 (Object Storage 는 프로덕션 것을 읽기전용으로)
   - 댓글/좋아요 데이터 존재
5. 소요 시간 기록 → RTO 목표(O04) 달성 여부 판정
6. 결과를 O04 문서에 기록 (날짜, 소요시간, 문제점)
```

훈련 중 발견한 문제는 **반드시 절차서를 수정**한다.
"다음엔 기억하겠다" 는 실패한다.

## 5. 의존성 갱신 정책

| 종류 | 주기 | 절차 |
|---|---|---|
| 보안 패치 (High/Critical) | **즉시** | 갱신 → `pnpm gate` → 배포 |
| patch 버전 | 월간 | 일괄 갱신 → 게이트 → 배포 |
| minor 버전 | 월간 | 일괄 갱신 → 게이트 → 배포 |
| major 버전 | 분기 | **하나씩** 갱신 → 게이트 → 별도 배포 |
| Node LTS | LTS 전환 시 | 별도 태스크로 취급 |
| ffmpeg | 필요할 때만 | 트랜스코드 결과 회귀 테스트 필수 |
| PostgreSQL major | 필요할 때만 | 백업 + 복구 훈련 후 |

### major 갱신 규칙

```
한 번에 하나. 이유: 문제 발생 시 원인을 특정할 수 있다.

절차:
1. 브랜치 생성
2. 해당 패키지만 갱신
3. CHANGELOG / migration guide 읽기 (건너뛰지 않는다)
4. pnpm gate 전체 통과
5. 스테이징 배포 + 수동 스모크
6. 프로덕션 배포 (단독 배포. 다른 변경과 섞지 않는다)
```

### ffmpeg 갱신 시 필수 회귀 테스트

ffmpeg 는 버전 간 출력이 미묘하게 달라질 수 있다.

```
1. 갱신 전 버전으로 기준 영상 3개(가로/세로/긴것) 변환 → 결과 보존
2. 갱신 후 동일 변환
3. 비교: 세그먼트 개수, 총 용량(±5%), 재생 가능성, 화질 전환
4. buildHlsArgs 스냅샷 테스트가 통과하는가 (인자 호환성)
5. 실제 브라우저 재생 확인
```

## 6. 데이터 정리 잡 목록

| 잡 | 대상 | 주기 | 보존 |
|---|---|---|---|
| `storage.cleanup` | 만료 업로드 세션 + 멀티파트 | 매시 | — |
| `storage.cleanup` | 고아 자산 (에피소드 미연결) | 일간 | 7일 |
| `storage.cleanup` | 실패 자산 원본 | 일간 | 30일 |
| `storage.cleanup` | 콜드 이전 (원본) | 일간 | 90일 후 |
| `db.purge` | 소프트 삭제 행 | 일간 | 90일 |
| `db.purge` | 만료 세션 | 일간 | 7일 |
| `db.purge` | 알림 | 일간 | 90일 |
| `db.purge` | 만료 인증 토큰 | 일간 | 즉시 |

**모든 정리 잡은 삭제 건수를 로그와 메트릭에 남긴다.**
어느 날 갑자기 0건이면 잡이 죽은 것이고, 갑자기 폭증하면 버그다.

### 정리 잡 안전 규칙

```
1. 삭제 전에 반드시 COUNT 를 로그에 남긴다
2. 한 번에 최대 1000건. 초과분은 다음 주기로.
   → 실수로 전체 삭제하는 사고의 피해를 제한한다
3. 프로덕션에서 처음 실행할 때는 DRY_RUN=true 로 건수만 확인
4. 삭제 대상 조건에 반드시 시간 조건이 있다 (created_at < now() - interval)
```

## 7. 성능 저하 대응 순서

```
1. 어디가 느린가 특정 (대시보드: HTTP / DB / 큐 / 스토리지)
   ↓
2. HTTP 가 느리다
   → 어느 라우트인가? (route 라벨별 p95)
   → 그 라우트의 DB 쿼리 시간은? → 3번
   → DB 는 빠른데 느리다 → 코드 프로파일링 (N+1, 직렬 await)
   ↓
3. DB 가 느리다
   → pg_stat_statements 로 쿼리 특정
   → EXPLAIN ANALYZE → Seq Scan 이면 인덱스 검토
   → 인덱스가 있는데 안 쓰이면 통계 갱신 (ANALYZE)
   → 그래도 느리면 쿼리 재작성
   ↓
4. 큐가 적체
   → WORKER_CONCURRENCY 증가 → 부족하면 노드 추가
   ↓
5. 스토리지가 느리다
   → CDN 캐시 히트율 확인 → 90% 미만이면 캐시 헤더 점검
```

**조치 전에 반드시 측정한다.** 감으로 인덱스를 추가하면 쓰기가 느려지고
디스크만 늘어난다. `_ISSUES.md` 에 [OBS-###] 로 측정값을 남긴다.

## 8. 유지보수 시 절대 하지 않는 것

| 금지 | 이유 |
|---|---|
| 프로덕션 DB 에 직접 UPDATE/DELETE | 되돌릴 수 없다. 스크립트로 만들고 스테이징에서 검증 후 실행 |
| 테스트를 skip 해서 배포 | 하네스 무력화 |
| "일단 재시작" 으로 원인 조사 생략 | 같은 장애가 반복된다. 재시작 전 로그/메트릭 스냅샷 확보 |
| 알럿 임계값을 올려서 알럿 끄기 | 문제를 안 보이게 만드는 것 |
| 백업 확인 없이 마이그레이션 | |
| 여러 변경을 한 배포에 섞기 | 원인 특정 불가 |
| `_ISSUES.md` OPEN 항목 방치 | 그 태스크가 영구 정지 상태로 남는다 |
